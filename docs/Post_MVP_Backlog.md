15. **KNOWN ISSUE (root cause fixed, class now guarded) — CI on `ubuntu-latest` is STRUCTURALLY BLIND to filename-case collisions, and one of them shipped to `integration` green while white-screening every macOS checkout.** *(Recorded 2026-07-28. Number 15 is the next unused one; nothing renumbered, per item 12.)* **What happened.** `apps/web/src/lessons/` shipped `MathPreview.tsx` (the React component, exporting `MathPreview`) beside `mathPreview.ts` (the ASCII-math parser, exporting `previewOf` and — as an `interface` only — `MathPreview`). Both arrived in `851c308`, which is an ancestor of `origin/integration` and **not** of `f534be8`, so this was not one branch's local mistake: it merged to the shared branch and then reached `evan/era-land-expansion` through a 181-commit forward-merge (`e82e38d`; `f534be8..e82e38d` is 182 commits counting the merge itself). On any **case-insensitive** filesystem Vite answers `MathAnswerColumn.tsx`'s `import { MathPreview } from "./MathPreview"` with the **parser**, whose `MathPreview` is a type and so is erased at runtime. The browser then throws at ES-module **link** time — `SyntaxError: The requested module '/src/lessons/MathPreview.ts' does not provide an export named 'MathPreview'` — and because a link error is not catchable by the importer, **the entire entry graph dies: `#root` is empty and the app is a white screen**, not a degraded lesson surface. Reproduced before the fix on a scratch dev server (`rootHtmlLength: 0`), and three separate agents had independently built local workarounds for it before it was diagnosed. **Why CI reported success.** `.github/workflows/invariants.yml` is `runs-on: ubuntu-latest`, and Linux filesystems are case-sensitive, so on the runner `./MathPreview` resolves to `MathPreview.tsx` and only ever to that: build green, suite green, merge green. **This class of defect cannot fail in CI, ever** — no amount of behavioural test coverage closes it, because the runner's filesystem is the thing that differs from the team's laptops. Anyone on macOS is exposed; anyone on Linux cannot see it. **Why `forceConsistentCasingInFileNames` is not the answer, since the next reader will assume it is.** It is set in `tsconfig.base.json` and was set throughout, and it **did** fire here (TS1261/TS1149, plus TS2693/TS1484 for the type-used-as-value) — so `npm run typecheck` was **red**, not green, and CI runs `npm run typecheck`, which means this merged green only if that red was never seen on the merging branch. But the flag is still not a general guard: **it only fires when two spellings of one file are pulled into the same TypeScript program by imports.** Here that took the parser's own test importing `./mathPreview` while the column imported `./MathPreview`. A colliding pair with a single importer, or none, is invisible to it; so is a collision between two **directory** names; and so is `foo.ts` beside `foo.tsx`, where no casing is involved at all and the winner is decided by resolver extension order (tsc's list and Vite's are not the same). Biome cannot help either — it lints one file at a time and never sees a sibling's name. **The fix and the guard.** The parser was renamed to `mathPreviewParser.ts` (with its test alongside, via `git mv`) so the component keeps the house PascalCase-for-`.tsx` convention; adding an explicit `.tsx` to the import was rejected because it leaves the collision in place for the next person. The standing guard is **`test/repoFileCasing.test.ts`**, in a new root `repo-hygiene` vitest project, and it is deliberately built so that **it fails on Linux**: it takes its inventory from `git ls-files` and folds case in JS, touching the filesystem for nothing, so its verdict is identical on the runner and on a laptop. Demonstrated red against `git ls-tree -r origin/integration` — pure git object data, no working tree — which is exactly what the runner checks out. **Note its primary assertion is NOT "no two paths differ only by case"**: `MathPreview.tsx` and `mathPreview.ts` differ in extension too, so a whole-path fold produces two different strings and **passes**, which is the trap in the obvious version of this test. The real check is over the case-folded **stem within a directory** — the namespace an extensionless specifier actually addresses — with the whole-path/directory case check kept alongside it, and count floors under both so neither can pass vacuously over an empty listing. **Residual gap worth someone's judgement:** the workflow's inert-extension path filter can skip the whole gate set for a change that touches only e.g. `.png`, so a collision between two non-code files could still merge unobserved; and per item 13's ownership finding, `OWNERS.md` still has no row for `apps/web`, though this guard is root-config/CI-adjacent and so reads as **Gabe's** lane.
