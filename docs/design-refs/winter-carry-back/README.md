# Carrying a winter back to the city: two frames at 1024x580

The rendered evidence for the fix to the team lead's twice-reported defect:

> *"also carry this damage back to my city still doesnt work; buildings arent affected and
> still look the same"*

That is a claim about a **rendered frame**, so it is owed one. No passing test discharges it:
`apps/web/src/city/carryBackReachesTheIsland.test.tsx` proves the button reaches the city's own
state and says nothing whatever about whether the buildings change.

**Both frames are 1024x580, the lead's own window, under `reducedMotion`.** The viewport is
half the evidence, and 1024x580 is the short, realistic screen the crisis surfaces are judged
on across `../crisis-panel-width/`, `../city-says-what-it-knows/` and `../zero-accuracy-winter/`.

## The frames

| # | Frame | What it is evidence for |
| --- | --- | --- |
| 1 | `1024x580-1-before-the-carry-back` | The island as the player left it: era one's six skill buildings and the hub, all standing, no crisis on screen |
| 2 | `1024x580-2-after-the-carry-back` | The **same mount, same camera**, immediately after pressing *"Carry this damage back to my city"* on a winter that took the settlement. Every building is drawn from the ruin template — a different silhouette, collapsed roof, snow on the rubble — and the crisis-damage panel offers *"Repair for 60 stone"* per ruin |

`measured-1024x580.txt` carries the numbers, regenerated by the run below.

## What the pair shows, and how the change is attributed

The whole-frame diff is **110,220 pixels, 18.56% of the window** — but a whole-frame number
cannot tell *"the buildings became ruins"* from *"a panel appeared on the right"*, and a
carry-back that reached the data layer and not the renderer would produce exactly the second.
So the test also measures a band holding nothing but the settlement (`330,80 320x290`: right of
the city-life column, left of the repair panel, below the top chips, above the Buildings
disclosure). **36,830 of that band's 92,800 pixels changed, 39.7% of it.**

**The floor was measured red rather than argued.** Give `CitySurface` a crisis-damage writer
that records nowhere — which is the shipped defect, a correct write landing where the island is
not drawn from — and the same run reports:

```
only 0 of the settlement band's 92800 pixels changed, so the buildings look the same and
only the chrome moved: expected 0 to be greater than 0.1
```

Zero. That is the lead's sentence in numbers, and it is also what proves the camera does not
move between the two frames: the band is bit-identical when nothing about the buildings changes.

## The one thing these frames deliberately do not settle

The dev-only *"Replay onboarding"* panel sits over the top-right corner and clips the crisis
panel's heading in frame 2. It is a dev overlay (`isDevPersistenceEnabled`) and is not on the
learner build, so it is left in the frame rather than hidden — hiding it would make the picture
prettier than the one a reviewer running the app actually sees.

## Retaking them

```
VITE_WINTER_SHOTS=1 npx vitest run --config vitest.browser.config.ts \
  apps/web/src/city/carryBackFrames.browser.test.tsx
```

Off by default for the reason `apps/web/src/winter/winterZeroAccuracy.browser.test.tsx`
records: a full shadow-mapped scene with seven GLBs left switched on in that suite starves an
animation-timing assertion in a *different* file rather than failing where it is. The always-on
claims about this fix are the jsdom ones — `carryBackReachesTheIsland.test.tsx`,
`carryBackComposition.test.tsx` and `devPersistence/crisisDamagePersistence.test.ts`.
