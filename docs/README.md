# Calculus-Readiness City-Builder: Design Doc Manifest

> New developer? Start with [../ONBOARDING.md](../ONBOARDING.md). This file remains the detailed authority map for product and content specifications.

*This README is an executable manifest, not a marketing intro. It states what each doc governs, what is actually locked versus provisional versus missing, and the order in which things become safe to build against. Where it once overclaimed ("verified closed," "valid gain," "full product by Day 24"), those claims have been downgraded to what the files actually support.*

---

## 1. Product snapshot
A calculus-readiness diagnostic + remediation product built as a city-builder game: the city IS the student's math knowledge (domains = neighborhoods, skills = buildings, prerequisites = roads, mastery checkpoints = storms). Team of 3, ~24-day build.

## 2. Schedule and scope (aligned to the PRD timeline)
Two phases: **MVP done by Day 12, then ranked expansion toward the full product target by Day 24** (the target is `product_scope` ∈ {`mvp`, `target`} in `packages/skill-graph/src/skill_graph.json` — 62 nodes as of 2026-07-25; the old "48-node product ceiling" was superseded by the 2026-07-24 coverage expansion, PR #50). The MVP is **depth-first on Domain D1 (Real Numbers & Arithmetic): 6 nodes = 6 per-node lessons (1 node = 1 lesson = 1 building; reusing ~3 interaction archetypes)**, the one neighborhood built out deep (rich building types + resources), rather than shallow breadth across 9 domains. (Mentor guidance: depth over shallow breadth, one fully-realized neighborhood is a stronger demo and cleaner build than 9 thin ones.) Milestones (full detail in PRD §15 / MVP_Definition §8):
- **Day 2: skeleton gate** (frozen interfaces, registry wired, and D1 answer-checker capability spike run; much of the scaffold already exists, but the spike is still the next task).
- **Day 5: core loop closed** end to end (diagnose → build → storm → measurement writing records).
- **Day 9: all 6 D1 per-node lessons built** (reusing ~3 interaction archetypes) + rich D1 game layer + pre/post pipeline reproducibly computing a blueprint-matched D1 aggregate score difference on test input.
- **Day 12: MVP COMPLETE**, polished depth-first D1 foundational-readiness game, demoable.
- **Days 13-20: ranked breadth expansion** (pull the other 9 domains / remaining 56 `target` nodes in calc-proximal order).
- **Day 24: coherent ship at achieved breadth**, hardened, demo + handoff.

Pace is aggressive by design (AI-assisted velocity + existing scaffold/specs/registry). The full product target (62 in-product nodes as of 2026-07-25, per the registry) is the stretch ceiling; `Post_MVP_Backlog.md` defines coherent floor/likely/ceiling Day-24 ship states.

## 7. Locked engineering decisions (settled; do not re-litigate)
- Backend is AWS-native (Aurora Postgres + Cognito, all access via a Lambda); no realtime (single student, single screen).
- One mastery service is the only writer of `mastery`; evidence-based, monotonic.
- Client grades for instant UX; server recomputes for the authoritative metric.
- Mastery is accuracy-based (4 of 5 on a difficulty-balanced practice set), not a difficulty-tier gate. Hints count as correct; a full reveal does not.
- **Lessons are per node** (1 node = 1 lesson = 1 building); build reuse is via **interaction archetypes** (reusable lesson-interaction templates, invisible to the student), not by teaching multiple nodes in one lesson. **Placement routes the lesson entry point** (high `placement_estimate` → skip teaching → "prove it" practice), never the outcome — the building is always earned by evidence, nothing is pre-built. ## 8. Product hypotheses to validate (chosen designs, NOT beyond scrutiny)
These are deliberate design bets that usability testing should check, not locked facts:
- Timed storm battles feel like game tension, not test anxiety (kept intentionally; validate, don't pre-emptively remove).
- Students understand "placed high, zero confirmed mastery" without confusion.
- The 6 D1 per-node lessons (reusing ~3 interaction archetypes), built deep with a rich game layer, are buildable by Day 9 and the MVP is complete by Day 12 with three people. Ranked expansion may reach the full 62-node product by Day 24. (Aggressive; the core bet is AI-assisted velocity.)
- AI-assisted velocity may make the full 62-node stretch ceiling feasible, but human validation determines achieved breadth.

**On testing:** there is no efficacy *cohort* during the build (the team builds the measurement pipeline and hands off). This does NOT remove the need for lightweight *usability* testing during development, which the backlog correctly calls for.

## 9. How to run the invariant check
Run `npm run check:graph` from the repository root (exit 0 = pass). It reads `skill_graph.json` and checks: MVP set prereq-closed, MVP completable in a valid order, no cycles in the base hard-edge graph and the selected MVP-family projection, MVP count = 6 (all D1), no dangling/non-live prereqs, every in-product node has a lesson archetype (its node→template mapping; registry field `lesson_shell`, renaming to `lesson_archetype`). All counts (nodes, scope, archetypes) are computed from the registry and printed, never asserted.

**What this does and does not prove (precise):**
- **MVP closure is authoritative against the registry** (design data + test share one source).
- **Runtime drift protection is wired:** the TypeScript loader consumes `skill_graph.json` directly and the invariant test runs in CI. Future engines must keep importing the loader rather than copying registry data.
- The cycle check covers the base hard edges plus the *selected* MVP-family projection. For item-family nodes it includes only the declared `mvp_family`; families with no MVP selection contribute no edges. So it does not claim every possible post-MVP family graph is acyclic, only the base graph and the MVP projection. Fine for the 6-node D1 MVP (none of its nodes rely on unresolved item-family prereqs).

## 10. What the ship requirement actually is (corrected)
Not "a valid pre/post gain." Test input can only establish that responses are recorded, forms are scored, records are joined correctly, and a difference is computed reproducibly. So the requirement is:

> The pipeline can **reproducibly compute a blueprint-matched pre/post score difference from versioned test records.**

"Valid" (psychometric validity, form equivalence, real-learning claim) is reserved for a later empirical argument, not claimed at ship.

## 10a. MVP diagnostic scope (RESOLVED)
The MVP placement diagnostic assesses the **6 D1 (MVP) nodes only**, not the full in-product set (62 as of 2026-07-25; the older 40/48/56 labels are all retired), because the MVP is depth-first on Domain D1. Rationale: at ~2 items/node this is a short ~12-item diagnostic, matching the anxiety-sensitive requirement, and only D1 has built remediation at MVP. So:
- Placement diagnoses the 6 D1 nodes that have built remediation.
