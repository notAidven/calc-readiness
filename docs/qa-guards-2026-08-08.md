## 2. The findings, item by item

### D-1 · `classifyChipPalette.browser.test.tsx` — the self-counting list, still live

This is the `spotTheErrorPalette` trap verbatim, in a second file. The population is an
authored array of seven D5 visual ids, and the coverage assertion counts that array against
a literal in the same file:

```166:169:apps/web/src/lessons/classifyChipPalette.browser.test.tsx
test("the sweep covers every D5 board built from a set of named chips", () => {
  expect(NEUTRAL_CHIP_VISUALS.length).toBe(7);
  expect(new Set(NEUTRAL_CHIP_VISUALS).size).toBe(NEUTRAL_CHIP_VISUALS.length);
});
```

The only edit that can ever fail that line is an edit to the line above it. The file's own
docblock states the criterion behaviourally and correctly — *"a board that paints options
the learner has not picked yet"*, adding that *"a surface can carry a mechanic without
importing a line of it, so 'two' is not the criterion"* — and then scopes the sweep to one
domain anyway.

The prior round's claim that the guard **misses `RationalCombinedRateBuild` is STALE**: it
is the seventh entry at this SHA, added with the reasoning above. What is not stale is the
shape.

**Derivation.** 67 sources under `apps/web/src/lessons/interactive` render
`.lesson-interactive__chip`. The colours are not in those sources — all 67 read
`civic=false brick=false` — because `--brick` and `--civic` reach a chip through
`styles.css:6342` (`[data-state="wrong"]`) and `styles.css:6347` (`[data-state="solved"]`),
or through an inline style. That is precisely why the claim needs a rendered board rather
than a grep, and why a source-derived population is not enough on its own. 67 is the
candidate set; **a correct population owes one more filter — boards that offer live,
unpicked options at or reachable from mount** — and that filter has to be applied by
mounting, not by reading.

**Gap proven by injection.** `ExpDecayClassify.tsx` (D8, `exp-decay-classify`) styles an
unmarked chip with `const neutral = { color: LABEL, borderColor: LINE }`. Replacing that
with `{ color: "var(--civic)", borderColor: "var(--civic)" }` paints every option green
before the learner has touched the board — the exact defect. The guard, run exactly as it
ships:

```
 Test Files  1 passed (1)
      Tests  8 passed (8)
```

**The control.** Adding `"exp-decay-classify"` to `NEUTRAL_CHIP_VISUALS` with the same
defect in place gives:

```
AssertionError: exp-decay-classify: "Grows" is green before the learner picked it, so the board recommends it:
expected 'oklch(0.42 0.1 183)' not to be 'oklch(0.42 0.1 183)'
```

So every assertion in the file works. **The population is the only thing standing between
that defect and a red.**

**And the self-count actively resists the fix.** The same control run produced a *second*
failure:

```
FAIL ... > the sweep covers every D5 board built from a set of named chips
AssertionError: expected 8 to be 7
```

This is worse than an inert assertion. A guard that counts its own list does not merely
fail to notice growth; it makes correct growth fail, so the cheapest way past it is to
leave the eighth board out.

**Recommended population.** Derive from source via `kindFamily`'s `widgetsMatching`
(`/lesson-interactive__chip/`), which pulls the `BinaryRowSort` family in with it, then
filter at mount to the boards that offer two or more live, unpicked options. Floor the
derived set, and assert the composition beside the floor — specifically that the swept set
reaches more than one domain, since one-domain scoping is the failure this file already
has.

### D-2 · `widgetSuccessCoverage.test.ts` — the property is not the one being measured

Two independent gaps, one about the population and one about the predicate. The second is
the serious one.

**Gap (a): the predicate is satisfied by an import.**

```56:59:apps/web/src/lessons/widgetSuccessCoverage.test.ts
/** The one line a judged widget adds to join in. */
const CALLS_HOOK = /\buseWidgetSuccess\b/;
/** Delegating to an archetype counts: the archetype fires the badge itself. */
const USES_ARCHETYPE = /from "\.\/kinds\//;
```

`CALLS_HOOK` is a bare substring test over the whole file, and an
`import { ..., useWidgetSuccess, ... } from "../widgetMechanics"` line satisfies it. The
guard's own docblock describes the defect it is for: *"a widget missing it looks and
behaves fine, it just never confirms a correct step, and the learner gets silence where
every other widget pops a checkmark."* That is a claim about the badge **firing**.

Injected into `RationalizeExplore.tsx`, replacing its one `success();` call with
`void success;` — hook still held, badge never fires, lint-clean:

```
 Test Files  1 passed (1)
      Tests  292 passed (292)
```

**The control.** Removing the import as well (so the token appears nowhere) gives the red
the file is capable of, which locates the defect exactly on the token match:

```
AssertionError: RationalizeExplore.tsx neither fires the badge nor is listed as unjudged:
expected false to be true
 ❯ src/lessons/widgetSuccessCoverage.test.ts:89:7
```

**Gap (b): a judged surface sits outside the glob.** The population is three path patterns.
`cfu.tsx` — the end-of-lesson check, which grades a typed answer through the real checker —
is not one of them, and it does call `useWidgetSuccess` today. Nothing requires it to keep
doing so. Injected by replacing `const success = useWidgetSuccess();` in `cfu.tsx` with a
no-op:

```
 Test Files  1 passed (1)
      Tests  292 passed (292)
```

This is not a novel observation about `cfu.tsx`; it is one the sibling guard already
recorded and this one did not act on. `revealReAsk.test.ts:18-22` pulls the same file into
its own glob and says why: *"It is not under `interactive/` because it is not a board, which
is exactly how a path-shaped sweep loses a surface."*

**Why the browser sibling does not cover this.** `widgetSuccessDomains.browser.test.tsx`
drives the badge for real, and its docblock is explicit that it exists because *"a call can
be there and still be wired to the wrong branch"* — but it drives **three** widgets, one
each for D1, D5 and D7. For the other ~180 the source guard is the only thing standing
behind the badge, and it accepts an unfired hook.

**Recommended population and predicate.** Population: every source that judges an answer,
derived rather than globbed by path, with `cfu.tsx` and any future non-board judging
surface inside it. Predicate: the hook's **return value invoked**, not the identifier
present — the shape is `const success = useWidgetSuccess()` followed by a `success()` call
site, which is checkable from source. Where that is too weak, the honest answer is to widen
`widgetSuccessDomains` rather than to lean harder on a regex.

**Correctly built, and worth saying so:** the `UNJUDGED` list itself is exemplary and is
already cited as a worked example in `qa-verification.mdc`. It reads each excused widget's
source and fails if an excused widget has *gained* a badge, it floors the list against
emptiness, and it fails on an entry that no longer exists. That half needs nothing. The
scanner flag on `Object.keys(UNJUDGED).length).toBe(9)` was a **false positive**: that
string is inside the docblock at line 95, recording what the assertion used to be.

### D-4 · `SINGLE_BOARD` — the exemption's stated reason is false of four of its members

The file is otherwise one of the strongest in the repo: a liveness canary against a dead
`vi.mock`, a set-equality census in both directions, a split between an exemption
(`SINGLE_BOARD`) and a recorded debt (`POOL_OWED_IN_D1`) with a floor under each, and a
composition assertion (`variantDriven.length > NO_POOL_EXPECTED.length * 2`). **The prior
claim that `SINGLE_BOARD` is "not asserted in both directions" is STALE** — the census at
lines 484-485 asserts exactly that, and `POOL_OWED_IN_D1` carries its own both-way pair.

The gap is one level down, and it is the classic one. What the sweep observes is whether a
widget **asks `useWidgetVariants`**. What the file's property is about is whether **a
restart deals a different board**. Those come apart for a widget that reimplements the
cycle, and such a widget arrives with an empty `pool.seen`, is therefore indistinguishable
from a static diagram, and lands in an exemption list whose stated reason is *"Live visuals
that genuinely deal ONE board... a single fixed parameter set with no 'start over' to deal a
second."*

**Derivation.** Of the `SINGLE_BOARD` and `D1_SINGLE_BOARD` members, four hold a
multi-board array and cycle it out of local state: `rational-exclusion-classify` and
`rational-cursed-root-classify` (`BOARDS`), `rational-combined-rate-build` (`ROUNDS`), and
`linear-model-rate-explore` (`SCENARIOS`). The prior claim of "three rational widgets" is
confirmed and is one short. The file's own comment concedes the fourth in passing — the rate
explorer *"cycles two scenarios out of its own state rather than a pool"* — which is the
concession written down beside the exemption rather than acted on.

`RationalExclusionClassify.tsx` is the clearest: it hand-rolls the identical cycle.

```62:64:apps/web/src/lessons/interactive/RationalExclusionClassify.tsx
function boardAt(index: number): Board {
  return BOARDS[index % BOARDS.length] ?? (BOARDS[0] as Board);
}
```

```114:118:apps/web/src/lessons/interactive/RationalExclusionClassify.tsx
  function newBoard() {
    setBoardIndex((index) => (index + 1) % BOARDS.length);
    setCalls({});
    setFeedback(null);
  }
```

That `(index + 1) % length` is the same strict cycle the docblock says the whole guard rests
on: *"Cut a pool to one entry, or let a duplicate in, and every restart is a same-parameter
redraw."*

**Gap proven by injection.** Making `boardAt` return `BOARDS[0]` unconditionally turns every
"new board" into a redraw onto the numbers already on screen — the defect the file exists to
prevent. Run exactly as it ships:

```
 Test Files  1 passed (1)
      Tests  269 passed (269)
```

**Recommended population.** Keep the hook wrapper as the instrument, and add a second
population beside it: visuals that offer a restart affordance at all. A widget that offers
one and does not go through `useWidgetVariants` should have to be declared, with the same
both-way assertions the file already applies to its other two lists, rather than falling
into `SINGLE_BOARD` by the accident of an empty `pool.seen`. The four above are candidates
for a third list — a *reimplemented cycle* — whose members owe the distinct-boards
assertion driven through their own restart control.

### D-5 · `matchPairsDragDirection.test.ts` — a declared boundary, and it holds up

This one deserves a different verdict from the rest, and the difference matters.

**Derivation.** 16 `MatchPairs` importers in the population. Seven further sources under
`interactive/` pair exactly one `draggable` with exactly one `onDrop`, so the physical
asymmetry that makes the defect possible is present in all seven: `DiscriminantSorter`,
`ExpShiftDrag`, `GeoNetDrag`, `LikeRadicalsSorter`, `LikeTermsSorter`,
`RadicalQuotientSorter`, `StoneOrderSorter`. Three carry a directional instruction the guard
never reads, because it lives outside a `prompt="..."` prop — for instance
`RadicalQuotientSorter`'s *"Drag and drop each root into the bin for what its bottom number
does. You can also tap a root and then tap a bin."*

**But the guard already declares this, and argues it correctly**, at lines 66-70:

> Other boards under `interactive/` also drag (`ExpShiftDrag`, `CompleteSquareDrag`,
> `DifferenceSquaresDrag`, `GeoNetDrag`, the sorters, and the `LabelParts` and `FillTable`
> kinds), and they exhibit the same CLASS of defect, but each fixes its own geometry — tiles
> into slots, chips into bins — so "name the side" is not the rule that saves them and they
> are not in this population. That is a boundary drawn on purpose, and it is a gap.

The argument is sound. The rule this file enforces is *"say which side picks up"*, and that
rule is meaningful only because the `MatchPairs` kind fixes left-picks-up for all sixteen at
once. On a bin sorter the source is a tray and the target is a labelled bin, so the sentence
"drag a root into a bin" cannot be backwards in the way `InterceptRouteMatch`'s was. **I did
not inject here**, because an injected "backwards" sentence on a bin sorter would be
demonstrating that a rule nobody claims applies does not apply.

The residual is real and should be recorded rather than closed: those seven boards get **no
directional checking of any kind**, and the guard's own last sentence says what is owed —
*"a sweep for those owes its own reading of what each of them can and cannot receive."*
That is a separate guard with its own rule, not a widening of this one.

Everything else in this file is exemplary and needs no change: two exception lists making
two different claims, both asserted in both directions, a disjointness check, a
duplicate-path check, floors on the population and on the objectives, and — the part worth
copying — hand-read entries that record `actor`/`target`/`columns` so the assertions
**re-derive the human's claim from the sentence**, meaning a reversed prompt stops matching
its own exemption instead of hiding inside it.

## 4. Method, and what this stream did not do

**The sweep.** 946 test files under `git ls-files` were scanned for the tells: a population
from an authored array rather than derived from source; a count pinned rather than floored;
an exception list asserted in one direction or none; `toContain` with no count under it;
`test.each` over a possibly-empty population. The precise detector — `expect(X.length).toBe(N)`
where `X` is a literal declared in the same file — flagged 38 sites, most of them false
positives on locals computed from the tree. Within lesson and item-bank scope, exactly one
flagged site was the real trap: **`classifyChipPalette`**. No guard beyond the suspect list
was found to be mis-scoped; the two in-scope candidates I chased down (`loadBearingNotation`,
`d9.test.ts`) are in the table above as correctly built.

**Injection hygiene.** Five defects were injected across five files
(`CoordinateInterceptRead.tsx`, `cfu.tsx`, `RationalizeExplore.tsx`, `ExpDecayClassify.tsx`
+ `classifyChipPalette.browser.test.tsx`, `RationalExclusionClassify.tsx`). Each was
reverted immediately after its run and each revert verified with an empty `git diff` on the
file; `git status --porcelain` over `apps/web`, `packages` and `content` at the close of the
stream showed only sibling streams' untracked files. No injection was left live across a
long run, and no browser invocation exceeded a one-file list.

**NOT DONE, stated explicitly:**

- **D-5 was not proven by injection.** The reasoning is given above: the boundary is
  declared and the rule genuinely does not transfer to bin sorters, so an injection there
  would prove nothing. The seven-board residual is reported as an owed *separate* guard.
- **The behavioural population for D-1 is a candidate set, not a final one.** 67 chip
  sources is derived from source; the mount-time filter that narrows it to boards offering
  live unpicked options was not applied, because it requires mounting all 67 in Chromium.
- **D-3's 256 is the pair count, not the reachable count.** 61 pairs are live at both ends
  across ten domains against ~31 today, so the reachable gain from widening `POPULATION`
  alone is about 30. The rest needs extractor work per domain, unmeasured here.
- **No guard was widened or otherwise edited.** The one guard edit made
  (`classifyChipPalette`'s list, as a control) was reverted. Widening owes its own injected
  red at the changed lines, and that belongs to the fix phase.
